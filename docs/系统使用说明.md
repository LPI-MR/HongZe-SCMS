## 1. 系统概述与架构

泓泽供应链管理系统（SCMS）面向铁矿石供应链业务，覆盖 **矿山 → 海运 → 港口 → 铁路 → 中转 → 仓储 → 车队 → 钢厂** 全链条资源管理与订单全生命周期跟踪。

```
┌─────────────────────────────────────────────────────────────────┐
│                        浏览器（纯前端，无框架）                     │
│  16 个业务模块页面（HTML/CSS/JS）+ 公共层（导航/单位换算/数据层）     │
└───────────────┬─────────────────────────────────┬───────────────┘
                │ /api/* 业务读写（主存储路径）      │ HZData / HZFlowData
                ▼                                 ▼  适配器（历史预留）
┌───────────────────────────┐      ┌──────────────────────────────┐
│  server.js（Node 静态服务） │      │  PostgreSQL 16（Docker 容器）  │
│  监听 8000 端口 · clean URL │      │  库 HongZe-SCMS · 46 表        │
│  /api/* 数据层 + /api/futures│      │  5 个只读视图 · 审计台账        │
└───────────────────────────┘      └──────────────────────────────┘
```

> 数据链路：前端经 `common/hz-db.js`（HZDB 内存缓存基座）调用 `/api/*` 接口读写 PostgreSQL，启动时 `GET /api/bootstrap` 一次性拉取全量缓存。浏览器 localStorage 仅剩历史遗留键（客户旧键 hz_customers* 已于 2026-11-15 备份清理）。

**模块类型约定**（决定操作权限方向）：

| 类型 | 含义 | 涵盖模块 |
|---|---|---|
| **录入编辑类** | 支持新增/编辑/删除/状态流转 | 矿山、海运、铁路、中转、仓储、车队、钢厂（左侧菜单 1-9 中的 7 个物理维护模块）+ 客户、订单、合同、调度、价格指数上传 |
| **调用展示类** | 只读聚合展示，数据来自录入类模块 | 首页 KPI、订单跟踪、数据分析、合同看板、港口吞吐展示 |

## 2. 运行环境与启动步骤

### 2.1 环境要求

| 组件 | 要求 |
|---|---|
| Node.js | ≥ 18（原生 http 模块，无第三方依赖） |
| Docker Desktop | 用于 PostgreSQL 16 数据库（**必需，业务数据主存储**） |
| 浏览器 | Chrome / Edge 现代浏览器 |

### 2.2 启动步骤

```powershell
# ① 启动静态服务器（工作目录：项目根目录）
node server.js
# 输出：泓泽供应链管理系统已启动 → http://localhost:8000

# ② （可选）启动 PostgreSQL 数据库容器
docker start hongze-scms-db

# ③ 浏览器访问
# http://localhost:8000
```

> **说明**：`server.js` 支持 clean URL —— 访问 `http://localhost:8000/order-new` 自动映射到 `business/flow/order-new.html`。系统默认首页为 **新建订单页**（`business/flow/order-new.html`）。

### 2.3 数据库初始化（首次部署）

```powershell
# 应用全部数据库迁移（建库表结构）
node scripts/migrate.js up

# 导入演示种子数据
node scripts/seed.js up

# 校验导入结果（31 张表行数 + 外键完整性 + 视图连通性）
node scripts/verify-seeds.js
```

## 4. 快速上手：5 分钟走通新建订单

新建订单是系统业务主干的起点，一次提交将自动串联 5 个模块。

```
 新建订单页                       提交后自动联动
┌──────────────┐
│ ① 登录主体    │  自动填充
│ ② 货源信息    │  矿山(品类带出) + 港口 + 码头 + 船名 + 目的地级联
│ ③ 智能方案    │  公路/公铁联运/铁路直达 三方案自动计算
└──────┬───────┘
       │ 点击提交
       ▼
  1. 订单落库（状态：待港口，编号 HZyyyyMMddNNNN）
  2. 港口管理 —— 自动生成该订单的港口作业预填记录
  3. 运力管理 —— 3 条通道预填行（吨数/单价 0 待人工确认）
  4. 海运管理 —— 船名+货量齐备时自动生成航次（S-xxx，9 项船舶信息随单同步）
  5. 订单台账 —— 订单推进到「待确认」后同步进台账
```

**操作步骤**：

1. 左侧菜单点 **订单管理 → 新建订单**（默认首页即该页）。
2. 检查顶部登录主体横幅（绿色/蓝色为正常，红色为缺失需联系管理员）。
3. **货源信息**：搜索选择矿山（如「力拓」）→ 品类自动带出（只读）→ 选择接卸港（如「黄骅港」）→ 点选 1 个或多个码头 → 填写船名（如「远盛海 008」）。
4. **目的地**：站 → 库 → 钢厂 三级级联选择，路径条实时回显。
5. **智能方案**：货量 ≥ 某阈值时自动计算公路/公铁联运/铁路直达三种方案（含预估运费），缺参数时给出补齐提示。
6. **航运信息**：填写船公司/吨级/船型/航线/运行时间/海运单价/周期/发货方/收货方（9 项，将随单同步至海运航次）。
7. 点击 **提交订单**：成功浮层显示订单编号，可跳转「港口信息」或「订单详情」。

> ⚠️ 注意：**品类自动带出、不可手选**；吨位必须 > 0；船名留空则不生成海运航次。

## 5. 核心模块操作详解

### 5.1 客户管理

- **入口**：左侧菜单「客户管理」（客户台账）；公开注册入口 `register.html`。
- **功能**：维护客户主数据（贸易商/下游客户等），与订单页「目的地-钢厂」联动。
- **操作**：台账页「代注册客户」弹窗选择客户类型（集采贸易商/现货贸易商/下游客户）填写企业信息，保存即生效；公开注册页自主注册，提交后待平台审核，审核通过生效；台账列表支持查看/编辑/归类/审核/停用启用，待归类主体通过行内「归类」按钮（或编辑弹窗）确认客户类型。
- **数据**：权威存储为 PostgreSQL 表 `customer.customer`（经 `PUT/DELETE /api/customers` 读写），空启动；旧迁移流程遗留的待归类清单在打开台账页时自动并入客户库（来源标记「系统迁移」）。
- **写保护（keepStale 合并写）**：客户为无删除功能的主数据，API 采用合并写语义 —— 只合并提交行、跳过 stale 行清理，**缺行提交不会误删存量客户**（已修复此前「更新后数据消失」事故，详见第 9 章数据安全）。历史 localStorage 键 `hz_customers_v2` / `hz_customers_pending_v2` 已于 2026-11-15 全量备份（`C:\Users\Lenovo\Downloads\hz_customers_backup.json`）后从浏览器清理，源代码已无任何 hz_customers* 键读写。
- **数据补录移交事项**：存量客户的「联系人 / 电话 / 统一社会信用代码」字段部分为空，需业务侧逐户补录（代码无法代做）；补录入口 = 客户管理台账 → 编辑弹窗，保存即生效并同步入库。

### 5.2 订单管理（四步向导 + 状态机）

订单状态机共 **9 态**，单向推进（管理员可跳步）：

```
draft     →  port      →  capacity  →  plan      →  pending_confirm
(草稿)       (待港口)      (待运力)      (待方案)     (待确认)
                                                              │
completed ← shipped ← shipping ← confirmed ←──────────────────┘
(已完成)    (已发运)   (发运中)    (已确认)

台账同步点：pending_confirm 起的 5 个状态会自动同步至订单台账
```

- **四步向导**：新建订单 → 港口信息（order-port）→ 运力安排（order-capacity）→ 执行方案（order-plan），每步保存后进入下一环节。
- **状态流转**：详情页（order-detail）按角色流转；不允许回退；管理员可跳步。
- **数据**：键 `hz_flow_orders`（主干）等 9 键；订单编号当日流水递增。
- **删除订单**：级联清空港口/运力/航次关联数据，并通知台账移除。

### 5.3 价格指数管理

| 子页 | 类型 | 操作 |
|---|---|---|
| 汽运价格（truck） | 录入编辑 | 上传价格记录（含证据图片）、31 条演示数据 |
| 火运价格（rail） | 录入编辑 | 上传价格记录，16 条演示数据 |
| 铁矿石现货（iron-ore） | 静态展示 | 中矿国链港口现货快照（2026-05-25，20 条） |

**操作**：进入子页 → 点「上传数据」→ 填写日期/货种/起点/终点/单价/备注，可附证据图片 → 保存后列表刷新并进入最新指数卡片。

### 5.4 业务管理

- **总览（business）**：全局业务概览（调用展示）。
- **订单台账（orders）**：流程订单推进到「待确认」后自动入台账；支持人工补录、编辑状态（待确认/已确认/执行中/已发运/已完成/已终止）、关联车次与航次。9 条演示订单。
- **订单跟踪（tracking）**：按订单串联航次/车次的只读时间线展示。
- **结算管理（settlement）**：录入应收/应付结算单，关联订单与合同；8 条演示结算。

### 5.5 合同管理

- **合同台账（contracts）**：录入三方可贸易合同（甲方/乙方/丙方、金额、数量、执行进度）；5 份演示合同。
- **合同模板（templates）**：维护合同条款模板（含版本管理）。
- **合同看板（dashboard）**：签约/执行/回款聚合展示（调用展示）。

### 5.6 运输调度管理（录入编辑 + 自动联动）★

- **调度看板（transport）**：12 条演示车次（公路/铁路双模式）按节点推进（港口→中转→钢厂）。
- **调度录入（transport-entry）**：录入车次，可关联业务台账订单（HZ 单号）并自动带出货名；车次进度自动联动台账订单状态与状态日志。
- 详见 [第 7 章专项说明](#7-运输调度--业务台账-跨系统联动专项说明)。

### 5.7 数据分析

- **分析页（analytics）**：建设中。
- **调度分析（dispatch）**：车次/通道维度的只读聚合分析。

### 5.8 矿山管理（1 号模块 · 录入编辑）

- **入口**：`/mine`。
- **功能**：5 家矿山主数据（力拓/必和必拓/淡水河谷/福斯特库/西芒杜），含产品目录（43 条）、价格基准（30 条）、合作伙伴（19 条）、矿山故事、地图定位（Leaflet）。
- **操作**：新增/编辑矿山卡片 → 完善产品规格（品名/年产量/品位/杂质/水分/应用）→ 维护价格基准与合作伙伴。矿山的「品类映射」会直接驱动订单页品类自动带出。
- **数据**：键 `hz_mines`。

### 5.9 海运管理（2 号模块 · 录入编辑 + 自动同步）★

详见 [第 6 章专项说明](#6-海运管理模块专项说明)。

### 5.10 港口管理（3 号模块）

- **功能**：2 家港口（黄骅港/青岛港），港区划（12 个）、集疏运通道（4 条）、吞吐展示页。

- **数据**：键 `hz_railway_suppliers`。

### 5.12 中转站点管理（6 号模块）

- **功能**：3 个中转站（曹庄镇站/武安站/康城站），站点概况、 metrics、铁路线延长工程说明。

- **数据**：键 `hz_transfer_stations`。

### 5.13 仓储管理（7 号模块 · 四个子页）

| 子页 | 功能 | 种子 |
|---|---|---|
| warehouse | 仓储供应商概览 | 2 家 |
| suppliers | 供应商明细 + 垛位管理（12 垛） | 同上 |
| io | 进销存台账 | 空启动 |

- **操作**：编辑供应商（吞吐/库容/面积/设施）；垛位绑定矿种与吨数（吨数格式如「2.5万吨」）；矿种下拉含 14 种铁矿石（PB粉/PB块/纽曼粉…）。
- **数据**：键 `hz_warehouse_suppliers_v1`、`hz_warehouse_ores_v1` 等 5 键。

### 5.14 汽运车队（8 号模块）

- **功能**：2 家车队（自营/合作/外协），运力规模、最低保障、最大运能。
- **操作**：编辑车队信息；公路方案运力引用车队名录。
- **数据**：键 `hzwl_fleets_v2`。

### 5.15 钢厂管理（9 号模块）

- **功能**：11 家钢厂（天铁集团/普阳钢铁/新兴铸管等），产能、矿石需求、注册资本、主营产品。
- **操作**：编辑钢厂档案；目的地级联的「钢厂」选项与客户库联动。
- **数据**：键 `hzwl_steels_v2`。

## 6. 海运管理模块专项说明

> **本模块是全系统唯一接收多来源自动同步数据的模块**，页面为「航次看板 + 港口现货 + COA 质检」三合一。

### 6.1 页面结构

```
┌─ 海运管理（/ocean）─────────────────────────────┐
│ ① 航次看板    6 个航次卡片（S-001 ~ S-006）        │
│    状态: 待装船/装船中/在途/已到港/已完成            │
│ ② 港口现货    20 条现货快照（Fe/SiO2/Al2O3/P/S…）  │
│ ③ COA 质检    1 份证书（810190245，含 14 项检验项）  │
└─────────────────────────────────────────────────┘
```

### 6.2 航次数据的三个来源（同步规则）

```
来源 A：订单流自动同步（主通道）
  新建订单提交 → 船名 + 货量齐备 → 自动生成航次（编号 S-001 递增）
  同步内容：船名/货种/货量(吨→万吨)/装货港/接卸港 + 船舶信息 9 项
  幂等键  ：flow_ref（订单 ID）—— 同一订单重复保存只更新不重复生成

来源 B：订单台账关联
  台账订单选择航次（voyage_id）→ 海运侧航次挂接业务单据

来源 C：手工录入
  海运页直接新增航次（无业务单据来源，用于自有航线）
```

### 6.3 同步规则明细（R1 / AC-O09）

| # | 规则 | 说明 |
|---|---|---|
| 1 | 触发条件 | 订单**船名已填** 且 **货量换算有效（> 0 吨）**，二者缺一不同步 |
| 2 | 航次编号 | `S-` + 三位流水（S-001、S-002…），自动递增 |
| 3 | 船舶信息 9 项 | 船公司 / 吨级 / 船型 / 航线 / 运行时间 / 海运单价 / 周期 / 发货方 / 收货方，整组随单同步 |
| 4 | 状态独立 | 航次初始状态「待装船」，后续推进由海运模块维护，不随订单状态机联动 |
| 5 | 幂等更新 | 同订单再次保存（如修改船公司）→ 更新既有航次，**不重复生成** |
| 6 | 单位换算 | 吨 → 万吨（如 70000 吨 = 17 万吨字段中的 7.0），换算非法不同步 |
| 7 | 级联删除 | 删除订单 → 自动清除其同步生成的航次 |
| 8 | 来源可溯 | 每条航次在数据库侧有同步映射记录（来源模块/来源单据/同步规则），见 `v_ocean_sync_view` |

### 6.4 数据库侧的同步映射

海运专用表 `ocean.ocean_voyage` + 同步映射表 `ocean.ocean_voyage_sync` 支持从其他业务模块的数据关联映射：

```sql
SELECT voyage_code, vessel_name, source_module, source_ref, sync_rule
FROM public.v_ocean_sync_view;

-- 演示种子输出（节选）：
-- S-001 | Pacific Glory  | order_ledger | HZ202608300001 | ledger_voyage_link
-- S-002 | Bulk Venture   | order_ledger | HZ202609140001 | ledger_voyage_link
-- S-006 | (手工录入演示航次) | manual       | (空)           | manual_entry
```

| sync_rule | 含义 | 数据来源 |
|---|---|---|
| `order_shipping_sync` | 订单航运信息同步 | 新建订单 vessel_info 9 项（浏览器侧 flow_ref 机制） |
| `ledger_voyage_link` | 台账挂接 | 订单台账 voyage_id 关联 |

### 6.5 操作注意事项

- 手工删除/编辑自动同步的航次不会回写订单；订单侧重新提交会再次同步更新。
- 港口现货为外部数据快照（来源：中国矿产·中矿国链），日期 2026-05-25，仅展示不可编辑。
- COA 证书支持证书头 + 多检验项结构，导入时按「证书 1 条 + 检验项 14 条」落库。

## 7. 运输调度 ⇄ 业务台账 跨系统联动专项说明

> **本联动打通「运输调度管理系统」与「业务管理系统（订单台账）」两条业务线**：车次进度自动驱动台账订单状态升级并写入状态日志，台账订单为车次提供关联候选与余量校验，消除两系统间的数据孤岛。

### 7.1 联动架构与数据流

```
┌─ 运输调度管理系统 ────────────┐        ┌─ 业务管理系统（订单台账）────────┐
│ transport-entry 调度录入       │        │ orders 订单台账                 │
│  · 新建车次（关联 HZ 单号）     │        │  · 状态：待确认→已确认→执行中    │
│  · 进度上报（节点逐级推进）     │        │         →已发运→已完成/已终止   │
│ transport 调度看板（只读）      │        │  · 状态日志 + 关联车次展示       │
└──────────────┬────────────────┘        └──────────────┬─────────────────┘
               │  trips-store.save()（联动唯一触发点）      │
               ▼                                         ▼
┌─ 数据基座（API 网关 + PostgreSQL，事务封装）─────────────────────────┐
│  PUT /api/trips      → ops.trip（车次表）                           │
│  PUT /api/ledger     → trade.order_ledger + trip_ids 关联子表       │
│  PUT /api/ledgerLogs → trade.order_ledger_log（状态日志）           │
└────────────────────────────────────────────────────────────────────┘
```

- **正向（运输 → 业务）**：保存车次时按关联订单分组重算台账状态，逐级推进并写联动日志；同步重建订单↔车次关联表。
- **反向（业务 → 运输）**：调度录入页的「关联订单号」直读台账订单清单（单号/货名/总量/剩余量/状态），选中后自动带出货名。

### 7.2 公共字段清单（直接映射，避免重复定义）

| 业务含义 | 台账侧（trade.order_ledger） | 车次侧（ops.trip） | 处理方式 |
|---|---|---|---|
| 关联键（订单编号） | `order_code`（HZ 单号） | `order_ref` | **直接复用台账单号**作为车次关联外键，车次不再维护独立 SO 编号 |
| 货名 | `cargo_name` | `cargo` | 选单自动带出，单一事实来源为台账 |
| 数量（吨） | `cargo_qty` | `tons` | 直接复用；剩余量 = cargo_qty − Σ 关联车次 tons |
| 操作人 | `order_ledger_log.operator` | — | 联动写入统一标记「运输调度系统」 |
| 时间 | `order_ledger_log.time` | `trip.time` | 毫秒时间戳，直接复用 |

### 7.3 差异字段适配转换

| 差异点 | 台账侧 | 车次侧 | 适配方案 |
|---|---|---|---|
| 状态模型 | 线性五态 + 已终止 | 节点链进度（铁路/公铁联运 9 节点、汽运 3 节点、自定义通道任意链） | `isDeparted()`：节点 ≥「发出」视为已发运，全部车次到终节点视为已完成；汽运链「发出」为第 0 节点（创建即发出） |
| 编号体系 | HZ202608150001（业务单号） | YS1115-013（调度流水号） | 不强行统一编号：关联经 `order_ledger_trip` 关联表映射，车次表冗余存 `order_ref` |
| 状态推进方向 | 人工编辑可置态/终止 | 节点逐级上报 | 联动只前向推进且逐级推进（每跨一级写一条日志）；「已终止」仅人工维护，联动侧做引用清洗 |
| 余量口径 | 订单总量 cargo_qty | 车次吨位可超出订单剩余量 | 车次提交时按剩余量预警（提示但不阻断，允许分批超计划调度） |
| 日志粒度 | 每次状态变更一条 | 每次节点上报一条 | 联动按台账侧粒度落日志；同一次保存跨多级时逐级补写 |

### 7.4 联动规则明细（R0–R5）

| # | 规则 | 说明 |
|---|---|---|
| R0 | 人工闸门 | 「待确认 → 已确认」为业务人工确认环节，联动不代劳（订单停留待确认时不推进） |
| R1 | 关联即执行 | 车次关联订单后，订单状态至少推进至「执行中」 |
| R2 | 发出即发运 | 任一关联车次到达「发出」节点 → 订单升级「已发运」 |
| R3 | 到库即完成 | 全部关联车次到达终节点 → 订单升级「已完成」 |
| R4 | 关联表重建 | `order_ledger_trip` 恒等于「车次按 order_ref 分组」的结果（车次为准，单向前向） |
| R5 | 引用清洗 | 已终止/已不存在的订单，其车次引用自动解除 |

- **幂等性**：每次保存按「绝对状态」计算目标（不依赖增量 diff），重复保存不产生重复日志、不重复推进。
- **审计**：每跨一级写一条台账日志，`operator = 运输调度系统`，备注形如「运输调度联动：车次 YS1115-013 已发出」。
- **容错**：联动异常不阻断车次保存本身（try/catch 隔离，车次落库优先）。

### 7.5 数据库侧的联动落点

| 表 | 作用 |
|---|---|
| `ops.trip` | 车次主表（含关联外键 `order_ref` = 台账 HZ 单号） |
| `trade.order_ledger` | 订单台账主表（status 由联动升级，trip_ids 关联子表随 PUT 重建） |
| `trade.order_ledger_trip` | 订单↔车次关联表（R4 重建） |
| `trade.order_ledger_log` | 状态日志（联动日志 operator = 运输调度系统） |

### 7.6 操作注意事项

- **联动触发点唯一**：仅调度录入页（transport-entry）保存车次时触发，与海运同步（浏览器侧幂等机制）同构；直接调 `PUT /api/trips` 不会触发联动。
- **台账日志为全量替换资源**：其它入口直接写台账日志可能被前端缓存覆盖（这也是联动逻辑放在录入页统一执行的原因）。
- **已终止订单**不出现在关联候选清单；已关联订单被终止后，车次引用自动解除（R5）。
- **订单详情抽屉**实时展示关联车次（如「YS1115-013（铁路直达 · 5/9）」），车次不存在时提示「待运输调度同步」。
- **超量预警**：车次吨位大于订单剩余量时仅提示不阻断（如需严格管控可后续加硬校验）。

## 8. 数据存储与持久化机制

### 8.1 当前主存储：PostgreSQL（经 /api/* 数据层）

前端经 `common/hz-db.js`（HZDB 内存缓存基座）读写 `/api/*` 接口：启动时 `GET /api/bootstrap` 一次性拉全量缓存；`put(key, list)` 全量替换（`PUT /api/:res`）；`remove(key, id)` 单条删除（`DELETE /api/:res/:id`）。写失败时 toast 提示且缓存不动，页面数据保持现场供重试。

种子机制：各数据层内置种子常量 + 版本号（`__version` / `SEED_VER`），首次加载写入，版本变更自动重置。

### 8.2 模块类型与表结构设计差异（数据库侧）

| 维度 | 录入编辑类模块 | 调用展示类模块 |

### 9.5 数据安全与破坏性删除审计（2026-11-15 加固）

- **背景**：客户管理曾发生「更新后数据消失」事故 —— API 全量替换（PUT）的 stale 清理（`DELETE WHERE pk NOT IN`）在缺行提交场景下误删了存量行，且仅留 console 埋点无法回溯。已从三个层面加固：
- **① keepStale 合并写**：7 个无删除功能的主数据资源（customers / mines / ports / rails / stations / warehouses / steels）PUT 采用合并写语义，只合并提交行、跳过 stale 清理，缺行提交不再误删存量。
- **② 审计台账落库**：迁移 `V009` 新建 `audit.destructive_log` 表，所有破坏性删除路径（stale_cleanup / empty_wipe / truncate_wipe / single_delete）在业务事务内留痕（表名/操作类型/行数/被删主键），经 SAVEPOINT 兜底 —— 审计失败不阻断业务。查询示例：

```sql
SELECT occurred_at, table_name, op, row_count, row_ids
FROM audit.destructive_log ORDER BY occurred_at DESC LIMIT 50;
```

- **③ 客户旧键备份清理**：浏览器 localStorage 中 12 个 hz_customers* 历史键（含事故期间的数据残留）已全量备份至 `C:\Users\Lenovo\Downloads\hz_customers_backup.json`（回读校验通过）后清理，消除旧键覆盖写风险。
- **移交事项**：存量客户的联系方式/统一社会信用代码需业务侧在客户管理编辑弹窗逐户补录（详见 5.1 节）。

## 10. 常见问题 FAQ

**Q1：页面数据清空了？**
业务数据权威存储为 PostgreSQL（经 `/api/bootstrap` 启动时拉全量缓存），清除浏览器数据/无痕模式/换浏览器不影响数据库数据，刷新后自动回填。若数据库侧数据异常，先查审计台账 `audit.destructive_log`（见 9.5 节）定位破坏性删除记录，再从备份恢复。

**Q2：新建订单品类下拉为空？**
矿山管理模块数据缺失。检查数据库 mine.mine_info 是否有数据（`node scripts/verify-seeds.js` 校验），必要时重跑种子；页面缓存刷新（Ctrl+F5）后自动回填。

**Q3：提交订单报「登录主体缺失」？**
登录体系未接入的降级保护。当前版本会自动以平台运营方主体填充；若出现红色横幅，请联系管理员检查登录配置。

**Q4：海运航次没自动生成？**
检查两点：① 船名是否已填；② 货量是否 > 0。任一缺失都不会同步（防脏数据）。

**Q5：数据库连接失败？**
确认容器运行：`docker ps` 查看 `hongze-scms-db`；未运行则 `docker start hongze-scms-db`。数据库名区分大小写，连接串需 `"HongZe-SCMS"`。

**Q6：迁移报「文件内容变更」？**
`meta.schema_migrations` 校验和保护检测到已应用版本的内容被修改。恢复原文件内容，或确认变更意图后联系运维重建版本（禁止直接改历史迁移）。

**Q7：种子重复导入会翻倍吗？**
不会。主表 ON CONFLICT 更新、从表 DELETE+INSERT，重复执行结果一致（幂等）。

## 11. 使用注意事项汇总

1. **品类自动带出**：订单页矿山品类由矿山管理模块映射生成，不可手动选择；映射缺失时提示联系运营维护。
2. **吨位校验**：订单货量必须为正数；0/负数/非数字均被拦截。
3. **状态不可回退**：订单状态机单向推进，仅管理员可跳步；删除订单会级联清理港口/运力/航次数据，不可撤销。
4. **台账同步时点**：订单推进到「待确认」才进入台账，之前的中间态不污染台账。
5. **海运现货只读**：港口现货为外部快照数据，不可编辑。
6. **数据库大小写**：库名 `HongZe-SCMS` 带连字符且区分大小写，SQL 中必须双引号包裹。
7. **禁止修改历史迁移文件**：校验和防护会拦截；新变更请新增 V00x 版本。
8. **浏览器兼容**：依赖现代浏览器 ES6+ 与 localStorage（仅历史遗留键/兼容读），不支持 IE。
9. **期货行情**：首页行情来自 `/api/futures` 新浪财经代理，公网不可用时页面降级显示。
10. **证据图片**：价格指数上传的证据图片存储于本地路径引用（`assets/seed/` 演示数据为占位路径）。
11. **主数据写保护**：客户/矿山/港口/铁路/中转/仓储/钢厂 7 类主数据为 keepStale 合并写 —— 缺行提交只新增不误删；这些模块页面无「删除」按钮，如需清理数据走数据库侧并会留审计记录。
12. **客户资料补录**：存量客户的联系人/电话/统一社会信用代码需业务侧逐户补录（客户管理 → 编辑弹窗），属业务移交事项。
