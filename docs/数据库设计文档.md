# HongZe-SCMS 数据库设计文档

> 文档版本：v1.0　编制日期：2026-11-13
> 目标数据库：PostgreSQL 16（Docker 容器 `hongze-scms-db`，库名 `HongZe-SCMS`，用户 `dev`，持久化卷 `hongze-scms_pgdata`）
> 设计依据：[系统模块清单](./系统模块清单.md) 中梳理的全部数据实体与 localStorage 键
> 迁移实现：`migrations/` 目录（V001 起，幂等可重复执行，附回滚与执行脚本）

---

## 1. 设计原则

1. **模块化 schema**：按业务域划分 schema，物理隔离、便于授权管理：
   - `meta` — 迁移台账与业务字典
   - `mine` — 矿山管理（菜单 1）
   - `ocean` — 海运管理（菜单 2，**独立专用表 + 数据同步映射**）
   - `port` — 港口管理（菜单 3）
   - `rail` — 铁路供应商管理（菜单 5）
   - `transfer` — 中转站点管理（菜单 6）
   - `wh` — 仓储管理（菜单 7）
   - `fleet` — 汽运车队（菜单 8）
   - `steel` — 钢厂管理（菜单 9）
   - `customer` — 客户管理
   - `trade` — 合同 / 订单（流程九表 + 台账投影）/ 结算
   - `pricing` — 价格指数管理（汽运 / 火运 / 铁矿石）
   - `ops` — 运输调度（车次）
   - `audit` — 破坏性删除审计（V009 新增，系统级留痕台账）
2. **主键策略**：沿用前端实体 id（TEXT，如 `mine-rt`、`o-seed-001`），保证种子数据零转换导入；流水/日志类表用 `BIGSERIAL` 自增。
3. **录入编辑类 vs 调用展示类的表结构差异**（核心设计约定）：
   - **数据录入编辑类模块**（矿山/海运/港口/铁路/中转/仓储/车队/钢厂/客户/订单/结算/合同台账/价格指数录入/调度录入）：建物理表，完整约束（NOT NULL / CHECK / UNIQUE / FK）、审计字段（`created_at`/`updated_at`）、触发器自动维护 `updated_at`；
   - **数据调用展示类模块**（首页、执行跟踪、调度数据分析、合同数据看板）：**不建物理表**，只建只读视图（`v_*`），数据全部来自上述业务表，保证单一事实来源，杜绝展示层二次写入口；
   - **静态展示数据的落库约定**：铁矿石价格指数为静态展示型模块，其数据仍落物理表 `pricing.iron_ore_index`，约定只读（页面无 CRUD），由 seed 维护。
4. **冗余快照列**：前端为展示性能普遍保存名称快照（`mine_name`、`contract_code`、`customer` 等）。数据库同时保留 **外键（权威）+ 名称快照列（展示）**，与前端行为一致，种子零失真。
5. **嵌套结构**：低频展示性嵌套（品牌故事、指标卡、基本信息、收费表、资质、审核历史等）用 `JSONB`；高频业务嵌套（矿山产品/价格参考/合作伙伴、港口分区/通道、垛位、COA 指标、订单车次关联）拆子表并建外键。
6. **幂等迁移**：所有 DDL 使用 `IF NOT EXISTS` / `OR REPLACE`，种子使用 `ON CONFLICT DO NOTHING/UPDATE`，可重复执行；每批次在 `meta.schema_migrations` 台账登记，支持正向执行与回滚。

## 3. 详细表结构

> 约定：所有表含审计列 `created_at timestamptz NOT NULL DEFAULT now()`；可更新业务表另有 `updated_at timestamptz NOT NULL DEFAULT now()`（触发器 `fn_touch_updated_at()` 自动维护）。下表仅列业务列。

### 3.4 port schema（港口管理，录入编辑类）

**port.port_info**（`hz_ports_data`）：`id PK、name NOT NULL、subtitle、photo、intro、metrics jsonb（指标卡）、basic_info jsonb（基本信息）、capacity jsonb（通过能力）、sort_no`。

**port.port_zone**（港区分区）：`id bigserial PK、port_id FK→port_info ON DELETE CASCADE、name NOT NULL、location、positioning、facilities jsonb、sort_no`；索引(port_id)。

**port.port_channel**（后方通道）：`id bigserial PK、port_id FK→port_info ON DELETE CASCADE、channel NOT NULL、route、via、cost、sort_no`；索引(port_id)。

### 3.5 rail schema（铁路供应商管理，录入编辑类）

**rail.rail_supplier**（`hz_railway_suppliers`）：`id PK、name NOT NULL、short_name、site、facts jsonb（关键事实）、intro jsonb（简介段落）、fees jsonb（收费 items/tables）、sort_no`。

**rail.rail_contact**（联系人）：`id bigserial PK、supplier_id FK→rail_supplier ON DELETE CASCADE、name、role、tel、sort_no`；索引(supplier_id)。

### 3.6 transfer schema（中转站点管理，录入编辑类）

**transfer.transfer_station**（`hz_transfer_stations`）：`id PK、name NOT NULL、subtitle、photo、intro、metrics jsonb、basic_info jsonb、station_intro、scale、sort_no`。

**transfer.transfer_yard**（堆场仓库）：`id bigserial PK、station_id FK→transfer_station ON DELETE CASCADE、name NOT NULL、area、capacity、location、sort_no`；索引(station_id)。

### 3.15 audit schema（破坏性删除审计，系统类 · V009 新增）

**背景**：客户数据「更新后消失」事故复盘 —— API 全量替换（PUT）的 stale 清理（`DELETE WHERE pk NOT IN`）属破坏性删除，此前仅留 console 埋点，无法事后回溯。V009 为**所有破坏性删除路径**建立统一审计台账，写入位于业务事务内，经 `SAVEPOINT audit_destructive` 兜底：审计表缺失或写入失败仅降级为 console 警告，不阻断业务写入。

**audit.destructive_log**

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | bigserial | PK | |
| occurred_at | timestamptz | NOT NULL DEFAULT now() | 发生时间 |
| table_name | text | NOT NULL | 被清理的业务表（schema.table） |
| op | text | NOT NULL | 操作类型（4 种，见下） |
| row_count | integer | NOT NULL DEFAULT 0 | 被删行数 |
| row_ids | jsonb | | 被删行主键数组（truncate 场景为 null） |
| detail | jsonb | | 预留：触发上下文扩展 |
| 索引 | idx_destructive_log_table_time(table_name, occurred_at DESC) | | 按表+时间倒查 |

**op 操作类型**：

| op | 触发路径 |
|---|---|
| `stale_cleanup` | upsert 模式清理「提交列表之外的行」（缺行提交场景） |
| `empty_wipe` | upsert 模式提交空列表触发的清空全表 |
| `truncate_wipe` | truncate 模式（流水/镜像类资源）PUT 前的全删 |
| `single_delete` | `DELETE /api/:res/:id` 单条删除 |

**配套：keepStale 合并写（API 引擎层语义，V005 引入、本次扩大启用面）**：`api/resources.js` 中标记 `keepStale: true` 的资源，PUT 采用合并写语义 —— 只合并提交行、跳过 stale 行清理，**缺行提交不会误删存量数据**（行不存在即新建，行已存在即更新）。当前启用资源（均为无删除功能的主数据）：**customers / mines / ports / rails / stations / warehouses / steels** 共 7 个。不启用的资源：有单条删除功能的业务资源（voyages/coas/settlements/ledger/fleets/contracts/templates/analyticsOrders/flowOrders）、事务性调度数据（trips）、truncate 模式的流水/目录类（ioRecords/customsRecords/oreCatalog）。

## 7. 数据类型与通用约定

- 金额：`numeric(18,2)`；吨：`numeric(14,3)`；万吨：`numeric(12,4)`；品位/百分比：`numeric(6,2)`。
- 时间：审计列 `timestamptz`（DB 默认 now()）；业务日期 `date`；前端传入的字符串时间（如 trips depart_time）按原格式存 `text`，保证种子零失真。
- 触发器：`meta.fn_touch_updated_at()` 统一维护 `updated_at`；每个可更新业务表挂载。
- 枚举：全部用 `CHECK` 约束（不使用 ENUM 类型，便于迁移期调整）。
- 排序：列表展示顺序用 `sort_no`（种子按前端数组序写入）。

## 8. 权限设计

- 应用账号 `dev`（Docker 环境变量给定）为库内 OWNER；
- 规范预留只读角色 `scms_reader`（仅 SELECT 业务 schema 与视图），迁移脚本自动创建并授权（幂等）。
