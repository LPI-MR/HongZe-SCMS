## 六、v1.3 客户数据事故复盘与数据安全加固（2026-11-15）

### 事故概述

业务反馈：客户管理「保存更新后数据消失」。排查确认客户库多条存量客户被静默删除，根因不在前端展示层，而在 API 引擎的全量替换写路径。

### 根因链路复盘

1. **写模式**：数据 API 化后，前端模块保存为「全量替换」—— 页面提交整个列表，`PUT /api/customers` 落库。
2. **stale 清理**：API 引擎 upsert 模式在写入提交行后执行 `DELETE WHERE pk NOT IN (提交行)`，用于清掉「提交列表之外的行」（语义上支持页面删除）。
3. **触发场景**：客户编辑弹窗的提交载荷只含**单个/部分客户**（编辑场景非列表维护场景），引擎按全量替换语义处理，将「未提交的存量行」全部识别为 stale 行删除 —— 一次编辑即抹掉其余客户。
4. **可观测性缺失**：该删除路径此前仅留 console 埋点，无落库留痕，事故发生后无法从系统侧回溯删除明细，只能靠浏览器 localStorage 残留数据反推。
5. **放大因素**：浏览器 localStorage 仍残留 12 个 hz_customers* 历史键，存在旧键覆盖写回的风险面（虽非本次事故直接根因，但属同类隐患）。

### 修复方案与落地（四项措施）

| # | 措施 | 产出物 | 说明 |
|---|---|---|---|
| 1 | **keepStale 合并写**（根治） | api/resources.js | 客户标记 `keepStale: true`：PUT 只合并提交行、跳过 stale 行清理，缺行提交不误删存量（行不存在即新建，已存在即更新）。API 实测：stations 缺行提交行数不变（4→4），单条删除恢复 3 |
| 2 | **破坏性删除审计落库**（可回溯） | migrations/V009__destructive_audit.sql + down、api/engine.js | 新建 `audit` schema + `audit.destructive_log` 表（occurred_at/table_name/op/row_count/row_ids jsonb/detail jsonb + 索引）；引擎 4 类破坏性删除路径全部留痕：stale_cleanup / empty_wipe / truncate_wipe / single_delete；写入在业务事务内经 `SAVEPOINT audit_destructive` 兜底，审计失败降级 console 警告不阻断业务 |
| 3 | **主数据 keepStale 扩大**（同类隐患收口） | api/resources.js | 与客户同性质的无删除主数据全部启用：mines / ports / rails / stations / warehouses / steels（共 7 资源）。不启用：有单条删除的业务资源、事务性 trips、truncate 模式流水/目录类 |
| 4 | **localStorage 旧键备份清理**（风险面消除） | 浏览器环境 + 备份文件 | 12 个 hz_customers* 历史键（合计 217,465 字符）全量备份至 `C:\Users\Lenovo\Downloads\hz_customers_backup.json`（388,155 字节，回读校验通过）后清理，残留 0；源代码已无任何 hz_customers* 键读写（hz-db.js 内存缓存 + /api/bootstrap） |

### 数据恢复

事故期间被误删的 22 行客户数据经 localStorage `hz_customers_v2` 残留快照提取，通过 `PUT /api/customers` 重新入库；数据库与页面展示核对一致。

| 验证项 | 方法 | 结果 |
|---|---|---|
| 单测 | `node --test tests/*.test.js`（逐文件运行） | 118/118 PASS ✓ |
| V009 迁移 | `node scripts/migrate.js up` | V009 执行 250ms 入台账 ✓ |
| 审计留痕 | API 触发三类操作后查 audit.destructive_log | 3 条记录（single_delete transfer_station / stale_cleanup fleet_info / truncate_wipe truck_price_index count=31）✓ |
